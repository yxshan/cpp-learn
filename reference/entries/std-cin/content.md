# `std::cin`

`std::cin` 是与 C 标准流 `stdin` 关联的预定义窄字符输入流对象。

## 快速信息

- 头文件：`<iostream>`
- 命名空间：`std`
- 类型：`std::istream`
- 标准：C++98 起

## 代表性声明

```cpp
namespace std {
extern istream cin;
}
```

## 什么时候使用

适合从标准输入按空白分隔读取数字、单词等格式化 token，并通过流状态控制处理流程。
需要保留空格、明确行边界或给出精细错误位置时，通常先用 `std::getline` 取得整行，再使用
专门的解析逻辑；二进制协议也不应依赖格式化 `operator>>`。

## 输入、状态与复杂度

格式化输入在启用 `skipws` 时通常先跳过前导空白，再按目标类型解析字符。到达输入
末尾会设置 `eofbit`；格式或范围转换失败可以设置 `failbit`；底层读取异常会设置
`badbit`。流的布尔转换等价于 `!fail()`，所以应直接测试提取表达式是否成功，状态规则
见 [`[basic.ios.members]`](https://eel.is/c++draft/basic.ios.members)。

初始化完成后，`std::cin.tie()` 指向 `std::cout`。输入前的 sentry 准备过程可以
刷新这个绑定的输出流，因此交互式提示通常能在等待输入前显示。

标准没有为通用格式化提取规定一个可套用到所有类型的统一时间复杂度。实际成本包括区域
设置相关解析、stream buffer 访问、目标类型转换以及外部输入设备等待；处理 N 个输入字符
至少要消费相应字符，但不能据此承诺固定的墙钟时间。

## 生命周期与并发

`std::cin` 在进入 `main` 前已经可用，并且不会在程序执行期间被销毁。读取操作会持续修改
流状态、缓冲位置和格式设置，因此一次调用得到的“成功”只描述该次提取；它不会冻结后续
输入。多个线程共享读取时，即使实现避免数据竞争，token 由哪个线程取得仍取决于执行顺序，
业务协议通常应由单一读取者解析后再分发。

后流处于失败状态；若还要继续读取，必须先按输入协议恢复状态并处理剩余字符。

## 失败恢复

一次格式错误后，后续提取不会自动恢复。`clear()` 只重置状态位，不会移除导致失败
的字符；完整恢复还需要根据输入协议处理剩余输入。

## 常见错误

不要写 `while (!std::cin.eof())`，因为 EOF 通常是在一次读取尝试后才被发现。使用
`while (std::cin >> value)`，让循环条件同时执行读取并验证结果。混用 `>>` 与
`std::getline` 时，还需理解前一次提取可能留下的分隔换行。

## 与 JavaScript 的区别

浏览器 JavaScript 没有与 `std::cin >> value` 对等的同步标准输入；Node.js 的
`process.stdin` 更接近异步字节流，通常先接收 chunk 再自行分词和转换。`std::cin` 的格式化
提取会阻塞等待字符、按目标 C++ 类型解析，并把失败记录在流状态中，而不是返回 Promise、
抛出 JavaScript 类型转换异常或用 `undefined` 表示所有失败。

## 相关内容

`<iostream>` 声明该对象；`std::cout` 用于标准输出。
