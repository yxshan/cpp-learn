# 选择顺序容器

顺序容器把同类型元素组织成线性序列。选择容器时，先区分必须满足的接口和生命周期
约束，再比较修改模式与工程性能；不要从“名字像队列”或某一个 Big-O 直接跳到结论。

## 默认起点

运行时可增长、主要尾部追加的普通序列，通常先评估 `std::vector<T>`：它支持常数时间
随机访问，普通 `T` 连续存储，尾部插入为摊销常数时间。连续布局通常有利于批量遍历，
但缓存效果是工程推论而非 ISO 性能保证，仍需使用真实数据测量。规范基础见
[`[vector.overview]`](https://eel.is/c++draft/vector.overview) 和
[`[vector.data]`](https://eel.is/c++draft/vector.data)。

“默认”不是“永远选择”。只要需求命中下面的强约束，就应重新评估候选。

## 先拆开三个概念

- **顺序**：元素按位置形成线性排列。
- **随机访问**：迭代器支持常数时间位移、距离和下标操作。
- **连续存储**：相邻迭代器对应相邻元素地址，可形成一段 `data()` 范围。

三者不是同义词。`std::deque` 是顺序容器并支持随机访问，但没有连续存储保证；普通
`std::vector<T>` 和 `std::array<T, N>` 才是这里的连续候选。`vector<bool>` 需要单独
审视，不能套用普通元素对象的连续模型。参见
[`[sequence.reqmts]`](https://eel.is/c++draft/sequence.reqmts)、
[`[deque.overview]`](https://eel.is/c++draft/deque.overview) 与
[`[array.overview]`](https://eel.is/c++draft/array.overview)。

## 决策顺序

1. **元素数量是否在编译期固定且始终恰为 N？** 是则先评估 `std::array<T, N>`。只有
   “最大不超过 N”但当前数量会变化，并不直接匹配 array。
2. **是否必须提供连续 `T` 范围或 `data()`？** 需要增长时先评估普通
   `std::vector<T>`；不要选择 deque。
3. **是否需要常数时间随机访问？** vector、array、deque 可以；list 和 forward_list
   不提供这一能力。随机访问与连续性必须分开问。
4. **增长主要发生在哪？** 仅尾部通常从 vector 开始；首尾都频繁且不需要连续存储时
   评估 deque；已知位置的频繁节点插入/删除才进入链式容器评估。
5. **需要跨修改保存什么？** 明确是元素引用、指针还是迭代器。它们可能按不同规则
   失效，尤其不能把 deque 的引用规则套给迭代器。
6. **是否已经拥有插入位置？** list 的单元素插入在给定有效位置后为 O(1)；若只有索引，
   先走到位置通常仍为 O(n)。参见
   [`[list.modifiers]`](https://eel.is/c++draft/list.modifiers)。
7. **差异对当前规模是否重要？** 标准复杂度按元素操作次数表达，不等于真实耗时；用
   目标元素类型、硬件和负载测量。

## 候选决策表

| 候选 | 大小模型 | 连续 | 随机访问 | 主要高效修改 | 首要边界 |
|---|---|---|---|---|---|
| `array<T, N>` | 编译期固定 | 是 | O(1) | 不改变元素数 | `N` 是类型一部分；swap 线性；`N == 0` 有特殊边界 |
| `vector<T>` | 运行时可增长 | 普通 `T` 是 | O(1) | 尾部摊销 O(1) | 重分配；首部和中间修改线性；`bool` 特化例外 |
| `deque<T>` | 运行时可增长 | 否 | O(1) | 两端单元素 O(1) | 不能作为单段缓冲区；失效规则较细 |
| `list<T>` | 运行时可增长 | 否 | 不支持 | 已知位置单元素插入/删除 O(1) | 找位置通常 O(n)，逐节点存储 |
| `forward_list<T>` | 运行时可增长 | 否 | 仅前向 | 已知前驱后插入/删除 O(1) | 无 `size()`、无反向遍历，需要前驱位置 |

表中的布局和复杂度来自各容器 overview 与 modifiers。连续布局可能改善局部性、链式容器
可能产生节点分配等说法属于工程判断，应通过测量验证，不能伪装成标准保证。

## 失效速查

| 操作 | `vector` | `deque` | `list` / `forward_list` |
|---|---|---|---|
| 尾部插入 | 重分配则全部观察位置失效；否则旧 `end()` 失效 | 所有迭代器失效，已有元素引用/指针有效 | 其他元素的迭代器/引用有效 |
| 首部插入 | 线性；插入点及之后失效，重分配则全部失效 | 所有迭代器失效，已有元素引用/指针有效 | 其他元素的迭代器/引用有效 |
| 中间插入 | 重分配则全部；否则插入点及之后失效 | 所有迭代器、引用和指针失效 | 其他元素的迭代器/引用有效 |
| 删除元素 | 删除位置及之后的迭代器和引用失效 | 端点与中间规则不同，进入具体页面核对 | 只使被删元素的迭代器/引用失效 |

这张表用于筛选候选，不替代具体 API 的完整规则。尤其是旧 `end()`、删除范围与 deque
端点删除需要分别检查。规范依据：
[`[vector.modifiers]`](https://eel.is/c++draft/vector.modifiers)、
[`[deque.modifiers]`](https://eel.is/c++draft/deque.modifiers)、
[`[list.modifiers]`](https://eel.is/c++draft/list.modifiers) 和
[`[forward.list.modifiers]`](https://eel.is/c++draft/forward.list.modifiers)。

## 常见陷阱

- “需要 O(1) 下标，所以必须 vector。”deque 也支持随机访问，连续性才可能是区分项。
- “需要稳定引用，所以必须 list。”deque 端点插入也保留旧元素引用，但不保留迭代器。
- “list 任意位置插入 O(1)，所以按索引插入也快。”到达位置的成本被漏掉了。
- “固定最大数量就应使用 array。”array 表达的是元素数始终固定。
- “reserve 能让 vector 永远不失效。”它只限制容量范围内的重分配；中间插入仍会使
  插入点及之后失效。
- “标准写 O(1)，实际一定更快。”渐进复杂度没有包含所有分配、布局和硬件成本。

## 与 JavaScript 的区别

JavaScript `Array` 同时承担大多数动态序列用途，运行时也不会暴露 C++ 迭代器失效与
连续 `T*` 互操作约束。C++ 容器选择会进入公开类型、内存布局和生命周期契约，因此应按
调用方需要的能力选择，而不只是替换一种数组语法。
